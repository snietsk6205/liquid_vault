# Decisions

Every choice made without asking Med, newest at the bottom. "(open, Qn)" means a question in `docs/QUESTIONS.md`
still decides it (work continues with the default meanwhile). "Revises Dn" when a decision replaces an earlier one.
Med's own architecture decisions are in `docs/BRIEF.md` and are not repeated here.

|---|---|---|---|---|
| D1 | 2026-11-24 | App id `dev.liquid.vault`, name "Liquid Vault", GPL-3.0 (from the brief). Versions start at 0.1.0 for the Phase 0 build. | Brief. | High for the id (a new id is a new app, the Vault must be rebuilt); none for the rest. |
| D2 | 2026-11-24 | minSdk 33, targetSdk 33, compileSdk 37; AGP 9.3.2, Kotlin 2.4.10, Compose 1.12.1, Material3 1.4.0 — exactly Liquid Launcher 0.16.0's versions. | House style (liquid-android): a sideloaded personal app gains nothing from newer enforced behaviour; these versions are proven to build in the launcher's CI. Target 33 also keeps `wipeData` removing the work profile as documented for profile owners. | Low. |
| D3 | 2026-11-24 | Modules `app`, `core/common` (plain logic, JVM unit tests), `core/designsystem` (the Liquid kit copied from the launcher's `core/designsystem` + `DebugLog`/`Changelog`, package renamed, names such as `LauncherIcon` kept). No settings registry yet (Phase 4). | Skill: copy the kit; keeping names lets later kit changes be copied as they are. | Low. |
| D4 | 2026-11-24 | **Signing only from GitHub secrets** `SIGNING_KEYSTORE_BASE64`, `SIGNING_STORE_PASSWORD`, `SIGNING_KEY_ALIAS`, `SIGNING_KEY_PASSWORD`; nothing is committed. Without them CI signs with a throw-away key, names the APK `…-test-key.apk`, and the release job refuses to publish. **(open, Q1)** | The brief asks for the launcher's keystore with "the same secret names", but the launcher has **no** signing secrets: its keystore and passwords are committed (launcher D19), and **both repositories are public**, so that key is public. A public key would let anyone sign an app that passes the Vault's signature-level permission (Phase 5) or installs as an update. | Low now (no release yet); after a release, changing the key means reinstalling (and rebuilding the Vault). |
| D5 | 2026-11-24 | One APK, two copies: the personal copy (controller) and the Vault copy (profile owner), each with its own Diagnostics for its own side; components that belong to one side are switched per user at start (`SideComponents`). | Component state is per user; this is how Insular runs one APK on both sides. | Medium. |
| D6 | 2026-11-24 | Shell client: the **official Shizuku client API 13.1.5** (newest published, Sept 2023). The app opens **two doors** for the server's binder: `dev.liquid.vault.shevery` (Shevery's own client protocol: permission `com.hamondev.shevery.permission.PRIVILEGED_API` + meta-data `com.hamondev.shevery.client.PRIVILEGED_API_SUPPORT`) and `dev.liquid.vault.shizuku` (the official protocol; the library itself requests `moe.shizuku.manager.permission.API_V23`). Check S1 reports which door Shevery used. Commands run through the server's public AIDL `IShizukuService.newProcess` with argument arrays. | Read Shevery's source (HmnDev-Tech/shevery, Shevery-API): its server finds clients by either permission, sends the binder to `<pkg>.shevery` first and `<pkg>.shizuku` as fallback, with both extra keys, and keeps the binder descriptor `moe.shizuku.server.IShizukuService`. Requesting (never defining) these permissions is the client protocol; nothing of Shizuku's name, icon or app id is copied. | Low: drop a door after Phase 0 shows which one Shevery uses. |
| D7 | 2026-11-24 | Vault creation: Android's setup first (`ACTION_PROVISION_MANAGED_PROFILE`, all system apps left enabled, education screens skipped), the shell as fallback with Insular's manual steps (`pm create-user --profileOf 0 --managed Vault`, `pm install-existing --user N`, `dpm set-profile-owner --user N` (no `--name`: Android 14 rejects it, emulator run 4), `am start-user -w N`) plus one more: `am start --user N … FINISH_SETUP` so the Vault copy finishes its setup with a screen in front. Both refuse while any work profile exists. | Brief; Insular's documented manual setup. Leaving system apps enabled keeps both paths similar for the test. | Low. |
| D8 | 2026-11-24 | **The channel** between the copies = Insular's Shuttle idea: each copy holds a persistable `READ|WRITE|PREFIX` URI permission to the other copy's own `ChannelProvider` (`content://<user>@dev.liquid.vault.channel`), handed over in the intent (and its result) of a cross-profile activity start. Two ways are tried: a cross-profile intent filter for our own action (both directions; the result carries the answer's permission) and `CrossProfileApps.startActivity` (Vault → personal only, Android returns no result through it). The Vault copy connects by itself the first time it is opened after setup. | No shell, survives reboots (URI grants are persisted by the system), proven by Insular on many phones. | Medium. |
| D9 | 2026-11-24 | The AOSP default cross-profile intent filters are **not** copied from Insular. | Since Android 13 the framework sets them for every managed profile, also one made with `pm create-user` (AOSP `UserTypeFactory`); Insular's copy is for older Android and maps every filter to one direction. | Low. |
| D10 | 2026-11-24 | App-ops for Vault apps are also tried **as profile owner, without the shell**: AOSP's `AppOpsService.enforceManageAppOpsModes` lets a profile owner change modes for apps in its own profile; `AppOpsManager.setMode(int,int,String,int)` and `strOpToOp` are hidden but `@UnsupportedAppUsage` without a target limit, so reflection reaches them. Modes are read back with the public `unsafeCheckOpRawNoThrow` (no permission needed). The setup uses it to allow `INTERACT_ACROSS_PROFILES` for the Vault copy. | If MagicOS keeps this AOSP rule, storage rules for Vault apps need no shell at all (brief decision 2). | Low. |
| D11 | 2026-11-24 | Check statuses: PASS, FAIL, SKIPPED (with the reason), NEEDS YOU (a question with answer buttons), INFO, NOT RUN, RUNNING. Results saved per copy as one JSON file written whole and renamed. | Brief; house rule "no data loss". | Low. |
| D12 | 2026-11-24 | The harmless policy (P1) is "block screenshots in the Vault": on, read back, off, read back. | Visible, harmless, readable back with a public getter, leaves nothing behind. | None. |
| D13 | 2026-11-24 | `AutomationActivity` lets CI run checks from adb; it is exported but guarded by `INTERACT_ACROSS_USERS_FULL`, which only the shell and the system hold. Destroy still needs the typed phrase (`--es confirm DESTROY_VAULT`). | The emulator test must drive the real code paths; no app can reach it, and the shell could do the same things directly anyway. | Low. |
| D14 | 2026-11-24 | Phase 0 bridge rule: Liquid Vault itself (either copy) and the system picker (it browses for the app you are using; Android does not tell a provider which app opened the picker) are allowed; packages on a per-copy allowed list are allowed; everything else is refused, and every access is logged. The test folder is read-only. | Brief decision 4 at Phase 0 size; Phase 2 replaces it with the full rules. | Low. |
| D15 | 2026-11-24 | Bridge A (Work tab) opens with parent→managed filters for `OPEN_DOCUMENT_TREE` (+ `OPEN_DOCUMENT`/`GET_CONTENT` for `*/*`), set by the Vault copy and removed by "Undo" (which also puts the channel's filters back). Bridge B is a "Liquid Vault" root in the personal picker served by the personal copy through the channel. | Two mechanisms as the brief asks; A is what Insular's File Shuttle uses, B keeps the Work tab closed. Which works on MagicOS is decided from Med's report. | Low. |
| D16 | 2026-11-24 | Local builds in the cloud container redirect Maven Central to Google's public mirror through `~/.gradle/init.d` (not in the repository). | Maven Central rate-limits the container's IP (HTTP 429). CI uses the plain repositories. | None. |
| D17 | 2026-11-24 | Emulator test in two parallel parts on API 34: `vault` (Android's own setup tapped through, then everything without shell, a reboot and destroy) and `shell` (the official Shizuku server started over adb, then V2, C2, F6/F7, destroy). Bridges are tested by self-tests (the app reads its own providers), not through the picker's UI. | Proves the code paths on stock Android so that a FAIL on the phone points at MagicOS, not at the code. | Low. |
| D18 | 2026-11-24 | Android's setup (V1) is started with `EXTRA_PROVISIONING_ALLOW_OFFLINE = true`. | Emulator run 4: on Android 13+ with Google services, ManagedProvisioning hands work-profile setup to the "device management role holder" and shows "Can't set up device" when that holder is not ready, unless offline setup is allowed (AOSP `PreProvisioningActivityController.startAppropriateProvisioning`). The HONOR has Google services too. | None. |
| D19 | 2026-11-24 | `dpm set-profile-owner` is run without `--name`. | Emulator run 4: Android 14's dpm rejects it ("Unknown option: --name"); Insular's documented command has none. The Vault's setup sets the organisation name. | None. |
| D20 | 2026-11-24 | Cross-profile filter directions corrected: personal → Vault uses `FLAG_MANAGED_CAN_ACCESS_PARENT`, Vault → personal uses `FLAG_PARENT_CAN_ACCESS_MANAGED`. | Emulator run 5: the channel's intent did not resolve ("No Activity found"). AOSP `DevicePolicyManagerService.addCrossProfileIntentFilter` maps `FLAG_PARENT_CAN_ACCESS_MANAGED` to source = managed profile, target = parent: the names say whose activities may handle the other side's intents. Bridge A's picker filters had the same swap. | None. |
| D21 | 2026-11-24 | The CrossProfileApps way of connecting the channel needs `INTERACT_ACROSS_PROFILES` in both copies: the profile owner can grant only the Vault copy's; the personal copy gets it from Android's "Connected work & personal apps" page (button "Allow connected apps…" in L0) or from the shell. | AOSP `CrossProfileAppsServiceImpl.canInteractAcrossProfiles` checks the caller and the app in every target profile; a profile owner may change app-ops only in its own profile. The forwarded-intent way needs none of this. | None. |

| D22 | 2026-11-24 | V1 also watches for the new profile with Liquid Vault in it and finishes PASS as soon as it appears, whether or not Android's setup hands a result back (it waits 5 s more for one, then stops waiting and says so in the row). | Emulator run 7: Android's setup made the Vault and the Vault copy finished its setup, but no activity result ever reached the personal copy, so V1 waited forever. | None. |
| D23 | 2026-11-24 | The emulator test starts a check's screen a second time (clearing the app's task) when it has not started within 10 s, and prints a NOTE; a check that started is never retried. | Run 8: a check's screen started at the same moment as the Vault copy's first channel connection and stayed unstarted behind it (CI timing, not the app). `AutomationActivity` logs `AUTOMATION-START` so the test tells "never started" from "started and hung". | None. |
| D24 | 2026-11-24 | "Undo" for app-ops never writes the mode `default`. The shell path (F7) saves the Vault app's own entries before F6/F7's first change and puts them back (no entry → Android's default for the op, which removes it); the owner path (F5) sets Android's default for each op (it can read only the effective mode, not the app's own entry). Defaults: `allow` for the storage and media ops, `default` for All files (`StorageOps`). | Emulator run 10: after Undo, `appops get` showed entries in mode `default`; Android's default for the storage and media ops is `allow`, and a permission-backed op in mode `default` may read as "not allowed", so Undo could have left the app without storage. | None. |
